# ADR-011: Use a vector database (Qdrant or pgvector) for embeddings and RAG retrieval

## Context

LifeOS's AI orchestrator service needs to store and query dense vector embeddings for several first-class capabilities: semantic search across the document vault, RAG retrieval for the AI assistant, and recommendation memory for the algorithm engine. These workloads require approximate nearest-neighbor (ANN) search over vectors — typically 384–1536 dimensions depending on embedding model — with metadata filtering (e.g., "search only within this user's documents, this date range, this category"). This is a distinct access pattern from LifeOS's existing OLTP workloads (PostgreSQL for relational state, MongoDB for flexible documents, Redis for cache/session), and REQUIREMENTS.md already commits to a dedicated vector database rather than bolting ANN search onto an unindexed table. The requirements name two concrete implementations to choose between: Qdrant and pgvector. This ADR makes that choice.

## Options Considered

- **Qdrant (dedicated vector database)** — purpose-built ANN engine with tunable HNSW indexing, native payload filtering, quantization options, and a gRPC/REST API designed around vector workloads.
- **pgvector (PostgreSQL extension)** — adds vector columns and ANN indexes (IVFFlat/HNSW) directly inside the existing PostgreSQL instance already used for relational data.
- **Managed vector service (Pinecone, Weaviate Cloud)** — fully hosted, fastest to integrate, no infrastructure to operate. Not chosen because it introduces a paid external dependency and directly undercuts the project's "run everything yourself" portfolio goal — a core requirement is that LifeOS be self-hostable end to end without a managed-SaaS dependency for a core AI capability.
- **No dedicated vector store (brute-force cosine similarity in application code, or ELSER/keyword search only)** — not viable past a small corpus; O(n) full-scan similarity against every stored embedding does not scale past low tens of thousands of vectors at interactive latency, and keyword search alone cannot support semantic RAG retrieval.

## Decision Made

Use **Qdrant** as the dedicated vector database for embeddings, semantic search, RAG retrieval, and recommendation memory, deployed as its own service alongside the existing PostgreSQL/MongoDB/Redis stack. pgvector was evaluated and rejected as the primary store, though it remains a documented fallback for low-volume, latency-insensitive use cases if operational capacity is constrained.

## Why

The deciding factor is that vector search is not a peripheral feature of LifeOS — RAG retrieval and semantic search sit on the critical path of the AI orchestrator, which is one of the platform's flagship capabilities. That workload deserves an engine that treats ANN search as its primary responsibility rather than a bolt-on index type. Qdrant gives us HNSW parameter control (ef_construct, m, ef_search) to explicitly trade recall against latency per collection, native filtered search that pushes metadata predicates into the index walk (rather than post-filtering, which degrades recall as filter selectivity increases), payload-based multi-tenant isolation per user, and horizontal scaling via sharding/replication independent of the primary transactional database. pgvector's ANN indexes (especially IVFFlat, and HNSW prior to recent PostgreSQL/pgvector versions) historically show materially worse recall/latency tradeoffs at scale, and — critically — co-locating heavy vector index maintenance (index builds, revectorization on model upgrades) inside the same PostgreSQL instance that serves identity, finance, and calendar transactional traffic risks resource contention (CPU, I/O, autovacuum pressure) bleeding into unrelated, latency-sensitive services. Isolating the vector workload in its own service protects the blast radius of both sides.

## Tradeoffs

Choosing Qdrant means operating a new stateful service: another deployment, another backup/restore procedure, another set of dashboards, alerts, and capacity planning, and another failure domain the AI orchestrator must handle gracefully (timeouts, circuit breaking) when Qdrant is degraded. It also means two "sources of truth" to keep consistent — the canonical document/task/note lives in PostgreSQL or MongoDB while its embedding lives in Qdrant, so every write path that produces embeddable content needs a reconciliation strategy (outbox pattern via Kafka to keep Qdrant eventually consistent with the primary store) rather than a single transactional write. pgvector's rejected alternative would have avoided both of these costs — one fewer service, and vectors covered by the same PostgreSQL backup and transaction boundary as the source row — at the cost of a lower recall/latency ceiling and shared resource contention with OLTP traffic as embedding volume grows.

## Consequences

The AI orchestrator and document vault services take a hard dependency on Qdrant's availability for any RAG or semantic-search request; a Qdrant outage must degrade gracefully (e.g., fall back to keyword/full-text search or a "search temporarily limited" response) rather than fail the whole request path. Every service that produces embeddable content (documents, tasks, notes, calendar entries) must publish embedding-relevant change events to Kafka so a dedicated indexer consumer keeps Qdrant collections in sync with PostgreSQL/MongoDB — this is new infrastructure, not a side effect of existing writes. Qdrant collections must be partitioned per tenant (user) via payload filtering from day one to keep multi-tenant isolation and query latency predictable as the user base grows. Operationally, Qdrant joins the OpenTelemetry/Prometheus/Grafana stack as a monitored dependency with its own SLOs for query latency and index build time.

## When This Decision Would Be Wrong

This choice should be revisited if LifeOS's embedding volume and query rate stay small enough that the operational cost of a second stateful service outweighs its benefit — concretely, if total stored vectors stay under roughly 100K–500K and RAG/semantic-search query volume stays low (single-digit QPS), pgvector inside the existing PostgreSQL instance would likely meet latency and recall requirements with far less operational overhead, and running Qdrant would be over-engineering for the actual scale. It would also be wrong if the team operating LifeOS shrinks to the point where maintaining an additional stateful service is not sustainable (a solo-maintainer portfolio phase, for instance) — in that case, consolidating onto pgvector to reduce the infrastructure surface would be the more defensible engineering call, even at some retrieval-quality cost.

## How We Will Validate It

Before rollout, benchmark Qdrant against pgvector using a representative LifeOS embedding set (target: 500K vectors at 768 dimensions, matching a mid-size mainstream embedding model) on identical hardware: measure p50/p95/p99 query latency for filtered top-k search (k=10, with a realistic per-user payload filter) and recall@10 against exact brute-force ground truth, at HNSW parameters tuned for each engine. The decision is validated if Qdrant sustains p95 < 100ms with recall@10 ≥ 0.95 at the target vector volume under a sustained load test of at least 50 QPS, while pgvector is confirmed to fall short of at least one of those targets at the same volume — establishing the concrete performance gap that justifies the added operational cost. Post-launch, track Qdrant query latency, indexer consumer lag (event published to vector queryable), and collection size per tenant as ongoing production metrics, with an alert if indexer lag exceeds 5 minutes, since a stale index directly degrades RAG answer quality.
