# Why Flutter for the Mobile Client?

Upfront: the repository contains a bounded Flutter shell, not a releasable mobile client. It also
contains twelve independently packageable backend service modules. Their public surface is
currently REST (with generated gRPC contracts but no complete live gRPC mesh), and the shell is not
yet built into a full authenticated product workflow. This is the plan for when mobile work starts,
not something I can demo as a finished app.

The real constraint here isn't "what's the best mobile tech" in the abstract — it's that I'm one engineer (effectively) trying to ship three clients (Angular web, JavaFX/GraalVM desktop, mobile) on top of a backend that's the actual point of this project. LifeOS's differentiation budget is backend Java engineering — virtual threads, structured concurrency, microservices, event streaming, blockchain-integrity proofs — not mobile platform depth. So the mobile decision has to optimize for "real iOS and Android apps, sustainably maintained by a small team," not "maximum platform fidelity."

That rules out native Swift + Kotlin immediately: two languages, two UI toolkits, two release pipelines, two sets of platform bugs, for a surface I've explicitly decided not to compete on. It also rules out React Native, somewhat counterintuitively — the obvious argument for RN is JS/web synergy, but my web client is Angular, not React, so RN wouldn't share components or state patterns with anything I'm already building. It'd just be a third UI paradigm with none of the cross-client leverage that would justify it. I'm deliberately not leaning on a "Flutter is just faster/more mature than RN" claim here — both frameworks have moved a lot in the last couple of years (RN's New Architecture/Fabric changed its performance story materially), and I haven't benchmarked either against LifeOS's actual UI needs. The decision rests on the LifeOS-specific factors above (no Angular synergy for RN, one-engineer maintenance cost), not on a version-sensitive performance comparison I'd need to re-verify before repeating in an interview.

I seriously considered Kotlin Multiplatform Mobile, since it shares a JVM/Kotlin mental model with the Java backend and can share business logic across platforms while still rendering native UI. It's a genuinely close call, and I'd revisit it as it matures. I passed on it because full-UI KMM (Compose Multiplatform for iOS) is materially less proven than Flutter's rendering stack right now — smaller community, fewer production references, more risk of hitting unpaved paths specifically on iOS, which is the platform I most need to de-risk since it's not a PWA wrapper.

Flutter wins on the actual tradeoff: one Dart codebase targeting both platforms through its own GPU-composited rendering engine, mature widget system, strong iOS support, and a big enough community that I'm not debugging unpaved paths alone. The cost is real — Dart is a fourth language with zero type sharing against the Java backend, so API contracts need to be kept in sync via codegen (OpenAPI/GraphQL) rather than shared DTOs, and anything needing deep native integration (biometrics, background sync, native widgets) goes through platform channels, which is slower to build than calling the native API directly. I'm accepting that cost because it's smaller than the cost of maintaining two full native codebases on top of everything else this project is trying to prove.
