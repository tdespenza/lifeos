# Why Java 25?

If you ask me why Java 25 instead of Kotlin, Go, or Node.js, the honest answer is that this decision serves two goals at once: build a real, concurrent, I/O-heavy distributed system, and build something that reads well in a senior engineering interview. I want to be precise here rather than round up: Java 25 is the first LTS where virtual threads (finalized since Java 21) and scoped values (JEP 506, finalized in 25) are both stable, non-preview APIs. Structured concurrency (JEP 505) is *not* finalized yet in Java 25 — it's still a preview API in its fifth iteration, meaning it needs `--enable-preview` on both compilation and execution and its shape could still change again in a future release. I'd rather say that precisely than round it up to "everything's finalized," since getting a detail like that wrong is exactly the kind of thing that undermines credibility in an interview. What Java 25 does give me, even with structured concurrency still in preview, is virtual threads and scoped values as a stable foundation to build the fan-out story on, plus a JDK where I can start using `StructuredTaskScope` behind a preview flag today and expect the finalized shape to land in a near-future release rather than being years out. Building on Java 21 instead, where scoped values were also still preview and changing shape release to release, would mean the same moving-target problem without even getting the two APIs that are actually stable in 25.

I want to be upfront that I'm not exercising that fan-out concurrency in real code yet. Right now there are only two services — identity-service and task-goal-service — and neither has a concurrent fan-out code path. Virtual threads are turned on (`spring.threads.virtual.enabled=true`) in both, but structured concurrency and scoped values are an intentional next step once a service actually needs to fan out, not something I can point to in production code today. I'd rather say that plainly than imply I've already proven it out.

On the alternatives: Kotlin is a fine language, but running it as the primary language would dilute the "deep Java/JVM" signal I'm optimizing for, and it doesn't buy me anything Java 25 doesn't already have — its coroutines solve roughly the same problem structured concurrency solves. Go's concurrency model is great, but its type system is a weaker fit for the algorithm-engine work that's central to the portfolio goal — the goal dependency-order endpoint, for instance, is a real Kahn's-algorithm topological sort with cycle detection, and Java's sealed interfaces and pattern matching let me encode invariants there in a way Go's type system doesn't support as cleanly. Node.js was the easiest cut: single-threaded event-loop concurrency doesn't demonstrate the JVM-level concurrency depth I'm trying to show, and its type system is weaker for the same invariant-encoding reasons.

The honest tradeoff is that Java 25 is still recent — it reached general availability on September 16, 2025, so library and tooling compatibility (Web3j/Besu, GraalVM Native Image, APM/OTel agents) has had less time to mature than on 17/21. I'm validating each dependency explicitly rather than assuming compatibility, and pinning versions where I have to, rather than trusting that "LTS" alone means every third-party library has caught up.
