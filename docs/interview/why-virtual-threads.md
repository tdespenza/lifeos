# Why Virtual Threads?

Both services in LifeOS today — identity-service and task-goal-service — run with `spring.threads.virtual.enabled=true`. That's the whole implementation footprint right now: one config line per service. I want to be upfront that neither service does heavy concurrent I/O fan-out yet, so this isn't a decision I've stress-tested with real traffic. But it's a decision I made deliberately and early, because it shapes how I write code from day one, and retrofitting it later across a fleet of microservices would be much more painful than adopting it before there's much code to migrate.

The reasoning starts from the target shape of the system, not the two services that exist today. LifeOS is meant to grow into roughly a dozen Spring Boot services that are almost entirely I/O-bound — Postgres queries, Redis lookups, downstream service calls, LLM calls, blockchain proof submission. That's the textbook case virtual threads solve: a thread blocked on I/O releases its carrier thread instead of parking an OS thread — but that's conditional on the actual client/driver in use supporting unmounting, not automatic just because the call happens to be I/O. Standard `java.net` blocking sockets get this transparently, and the mainstream PostgreSQL JDBC driver (which both services actually depend on today) is built on that kind of blocking socket I/O. Redis isn't a dependency of either service yet, so I want to be careful not to pre-verify something I haven't added: Spring's default Redis client, Lettuce, is actually a Netty-based *asynchronous* client under the hood — its synchronous `RedisTemplate` API works by blocking the calling thread on a `RedisFuture`, which is a different mechanism than blocking socket I/O and needs its own check for virtual-thread behavior once it's actually added, not an assumption I can make now by analogy to JDBC. That's exactly why [ADR-001](../adr/ADR-001-use-java-25.md)'s "every blocking dependency must be verified as virtual-thread-safe, not assumed" is stated as a per-dependency rule rather than a one-time check — not something to take on faith for every client library across a dozen future services. The alternative I seriously considered was Spring WebFlux/Project Reactor, which I rejected because it means rewriting the entire call chain — controller, service, repository, every client library — in a non-blocking style, with Mono/Flux everywhere and stack traces that are much harder to read. For a project where I also want to show I can write clear, maintainable code, that cost wasn't worth it when virtual threads give me most of the scalability benefit while keeping the plain synchronous, thread-per-request programming model I already know from Spring MVC.

If someone pushes on "but you haven't proven this scales" — that's fair, and I'd say so directly. What I have today is two CRUD-shaped services with no concurrent fan-out, so virtual threads currently buy me correctness-neutral headroom, not a measured win. Where this actually gets tested is the first time a service needs to fan out — the obvious next case is a dashboard aggregation endpoint that calls several services concurrently, which is exactly the workload virtual threads and structured concurrency (a separate, related decision, and still a preview API — JEP 505 — as of Java 25) are meant for. I also know the sharp edges going in, and I want to get the current one right rather than repeat an outdated warning: as of JEP 491 (Java 24, carried into 25), ordinary `synchronized` blocks and methods no longer pin the carrier thread — the JVM now tracks monitor ownership on the virtual thread itself, so a virtual thread can unmount even while holding a monitor. Pinning still happens, but the remaining causes are narrower: executing native code (JNI), a foreign-function call, or class initialization/resolution (which itself runs through native frames) — cases where the JVM genuinely can't safely unmount. `ThreadLocal`-heavy patterns are a different, real concern — not because of leaking across requests, but because they don't compose with `StructuredTaskScope` fan-out — which is why request context is planned around `ScopedValue` instead, once there's request-scoped context worth propagating.
