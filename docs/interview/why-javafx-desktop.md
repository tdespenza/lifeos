# Why JavaFX + GraalVM Native Image for the Desktop Client?

Short answer up front: there is no desktop client yet. This is a planned decision from the roadmap, not something running today — LifeOS right now is two backend services (identity-service and task-goal-service), no UI clients of any kind. But since the question comes up in interviews, here's how I'd explain the reasoning.

The desktop client is supposed to run on Windows, macOS, and Linux, support offline-capable local workflows, and touch OS-level features like the file system and secure credential storage. The obvious "fast path" answer is Electron — reuse the Angular codebase, ship it in Chromium, done in a weekend. I rejected that, and the reasoning isn't purely technical, it's also about what this project is for. LifeOS is a Java-centric portfolio: every backend service is Java 25 on virtual threads with structured concurrency. If the desktop client is just Chromium plus Node, it contributes nothing to that story — it's a step backward from the engineering narrative I'm trying to build, not a shortcut.

So I chose JavaFX on Java 25, compiled ahead-of-time with GraalVM Native Image. JavaFX keeps the desktop client on the JVM, which means model classes and validation logic can in principle be shared with the backend without a serialization or FFI boundary crossing languages. GraalVM Native Image solves the two real objections to a JVM desktop app: slow cold start and having to bundle a JRE. I haven't built or measured a LifeOS Native Image binary yet, so I won't quote specific startup numbers as if I'd benchmarked this — GraalVM's own published figures put Native Image cold-start meaningfully faster than a cold-starting JVM (roughly an order of magnitude, not a fixed number I'd cite without a source), and closing that gap is exactly why I'd want it here. The real deliverable either way is a single self-contained executable I can wrap with `jpackage` into a real MSI/DMG/deb installer — cold-start numbers for LifeOS specifically belong in `docs/benchmarks/` once I've actually measured them, not asserted here.

The honest tradeoff, and the one I'd lead with in an interview: GraalVM's closed-world static analysis fights with reflection, and both JavaFX's FXML loader and Spring's DI container lean on reflection heavily. That means FXML views need generated reachability metadata that has to stay in sync with the view graph, and any backend module I want to reuse from the desktop side has to be plain Java with zero Spring annotations — I can't just declare a dependency on a Spring module and expect a native-image build to succeed. I considered Compose for Desktop (rejected — it drags in Kotlin and dilutes the Java-only positioning) and native Swift/C++ (rejected outright — zero Java skill demonstrated, and a second codebase with no backend code sharing).

I also considered whether Electron's much larger contributor pool and simpler tooling made it the more defensible engineering choice on its own merits — and if this project were optimizing purely for shipping speed with a non-JVM team, it would be. It isn't, so I didn't.
