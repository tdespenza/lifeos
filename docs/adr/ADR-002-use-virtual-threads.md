# ADR-002: Use virtual threads for high-concurrency I/O-bound workloads

## Context

LifeOS is composed of ~11 Spring Boot microservices (identity, profile, task/goal, calendar, finance, document vault, media streaming, AI orchestrator, algorithm engine, blockchain trust ledger, notification, analytics) exposed over REST, GraphQL, and gRPC. Nearly every request handled by these services spends most of its time waiting: PostgreSQL/MongoDB queries, Redis lookups, Qdrant vector search, Kafka/Pulsar produce-and-await, downstream gRPC calls between services (e.g. the AI orchestrator fanning out to the algorithm engine, profile service, and vector DB per recommendation), outbound calls to LLM providers, and blockchain proof submission to Besu. This is a textbook I/O-bound, high-fan-out workload profile, not a CPU-bound one.

Historically, the JVM has forced a choice between two unattractive concurrency models for this shape of workload: platform threads (one OS thread per request, capped at a few thousand before the JVM runs out of stack memory and the scheduler thrashes) or reactive/non-blocking programming (unbounded scalability, but a total rewrite of the programming model — Mono/Flux everywhere, no simple stack traces, no thread-per-request mental model, and every JDBC/HTTP client library needs a reactive-capable equivalent). Java 25 (built on the virtual threads work finalized in JDK 21+) offers a third option: keep the synchronous, thread-per-request programming model, but decouple logical threads from OS threads so blocking I/O no longer holds a carrier thread hostage.

Given that LifeOS is deliberately built to demonstrate senior/staff-level judgment, the decision needs to be justified on the actual shape of the workload, not adopted because it is new.

## Options Considered

1. **Platform threads + traditional thread pools (`ExecutorService`, Tomcat's default thread pool).** The status quo. Rejected as the primary model because the services are I/O-bound with high fan-out (AI orchestration alone issues 3-6 concurrent downstream calls per request). Platform thread pools cap concurrency at roughly `pool size` (typically a few hundred to ~1-2k threads per service before memory/scheduler overhead becomes prohibitive), which directly caps request throughput under load, independent of CPU or downstream capacity.

2. **Reactive/non-blocking stack (Project Reactor / Spring WebFlux).** Rejected as the default because it solves the same problem (thread-per-request doesn't scale under blocking I/O) at a much higher engineering cost: the entire call chain — controllers, service layer, repository layer, gRPC stubs, Kafka clients — must be non-blocking end to end, or a single blocking call silently starves the small, fixed event-loop thread pool. Debugging is harder (stack traces are stitched across operators, not linear), and the team would need reactive-safe drivers for every dependency (R2DBC vs JDBC, reactive Mongo driver, etc.), doubling the learning surface for a portfolio project meant to showcase clarity of engineering, not framework virtuosity.

3. **Async callback-based models (`CompletableFuture` chains).** Rejected as a general-purpose default because callback composition trades one problem (blocking threads) for another (callback-chain complexity, harder cancellation semantics, and easy-to-miss exception propagation across `.thenApply`/`.thenCompose` chains). It remains useful in narrow, explicit fan-out cases but is not adopted as the platform-wide concurrency model.

4. **Virtual threads (chosen).** Keeps the synchronous, imperative, thread-per-request programming model — the same code a platform-thread service would have — while the JVM multiplexes many virtual threads onto a small pool of carrier (platform) threads, unmounting a virtual thread whenever it blocks on I/O instead of parking an OS thread.

## Decision Made

Use virtual threads (`Thread.ofVirtual()`, Spring Boot's `spring.threads.virtual.enabled=true`) as the default execution model for request-handling threads across all microservices: REST controllers (Tomcat/Undertow virtual-thread executor), gRPC server request handling, AI orchestration task execution, and parallel service-call fan-out. Structured concurrency (`StructuredTaskScope`, covered separately in ADR-003) is layered on top for grouped fan-out/fan-in workflows.

## Why

- The workload is dominated by blocking I/O (DB, cache, vector search, message broker, downstream RPC, LLM calls), which is exactly the case virtual threads are designed for: a virtual thread blocked on I/O releases its carrier thread back to the scheduler pool instead of occupying it.
- It preserves the synchronous, debuggable, thread-per-request programming model the team already knows from Spring MVC — no rewrite to reactive types, no split "blocking vs non-blocking" driver ecosystem to maintain across 11 services.
- It scales concurrency to the order of hundreds of thousands of in-flight virtual threads per service on commodity hardware, removing the thread-count ceiling that made platform-thread pools the binding constraint on services like the AI orchestrator, which fans out multiple concurrent downstream calls per inbound request.
- It composes naturally with structured concurrency for the fan-out/fan-in patterns already required by dashboard aggregation, AI recommendation gathering, and blockchain verification workflows.

## Tradeoffs

- **No benefit for CPU-bound work.** The algorithm engine's compute-heavy paths (graph algorithms, scheduling optimization, ranking/scoring) do not benefit from virtual threads — those remain bound by the number of physical cores and should stay on a bounded platform-thread pool (`ForkJoinPool`/`ExecutorService`) sized to core count, not blown out to virtual-thread scale.
- **Pinning still exists, but not from `synchronized` anymore.** As of JEP 491 (Java 24, carried into Java 25), the JVM tracks monitor ownership on the virtual thread itself rather than the carrier thread, so an ordinary `synchronized` block or method no longer pins the carrier while a virtual thread blocks inside it — the classic "legacy `synchronized`-around-I/O degenerates back to platform-thread behavior" failure mode this ADR originally warned about is fixed at the JVM level on Java 25 and does not need a blanket `ReentrantLock` migration. Pinning still happens for a narrower set of cases the JVM genuinely can't unmount from: native calls (JNI, the Foreign Function & Memory API) and class initialization/resolution (which itself runs through native frames). Third-party libraries that shell out to native code — some older logging appenders, native compression/crypto bindings, some JDBC driver internals — are the real remaining audit surface, not `synchronized` usage in general.
- **`ThreadLocal` misuse gets expensive.** Patterns that were cheap on a bounded platform-thread pool (a few hundred threads) become a real memory and GC concern at virtual-thread scale (potentially hundreds of thousands of concurrent threads), particularly `ThreadLocal`-based tracing/MDC context and connection-affinity hacks. LifeOS uses `ScopedValue` (ADR-004) for request-scoped context (correlation IDs, tenant/user context for OpenTelemetry) instead of `ThreadLocal` on virtual-thread paths.
- **Connection pool sizing must be rethought.** HikariCP and similar JDBC pools were tuned under the platform-thread assumption that pool size ≈ min(desired concurrency, `cores * 2 + spindle_count`), because a blocked platform thread was itself a scarce resource acting as a natural throttle. Under virtual threads, the application can generate far more concurrent DB requests than the pool can serve; the connection pool becomes the real bottleneck and must be explicitly sized and monitored (pool exhaustion, wait time) rather than implicitly bounded by thread count. This shifts capacity planning from "thread pool size" to "downstream dependency capacity" — which is more correct, but requires deliberate tuning (per-service HikariCP `maximumPoolSize`, Kafka producer/consumer concurrency, gRPC channel/stream limits) that did not previously need explicit attention.
- **Tooling maturity.** Some APM/profiler integrations and thread-dump tooling are still catching up to virtual threads (thread dumps can be enormous and less immediately readable); this is expected to keep improving but is a real day-2 operability cost today.

## Consequences

- Every service's HTTP and gRPC server thread pools move to virtual-thread executors; no service-specific platform-thread-pool tuning is needed for request-handling threads.
- The algorithm engine and any other CPU-bound module explicitly opts out with a dedicated, core-count-sized platform-thread/`ForkJoinPool` executor, documented at the call site so future contributors don't "helpfully" move it to virtual threads.
- No blanket `synchronized`-to-`ReentrantLock` migration is required on Java 25 (JEP 491 removed ordinary monitor pinning); instead, any dependency that calls into native code (JNI/FFM) on a request-handling path must be identified and evaluated for pinning risk specifically, via the JFR pinning-event monitoring below — not assumed safe or unsafe by inspection alone.
- `ThreadLocal` usage for request context is disallowed on request-handling paths in favor of `ScopedValue`; this is a lint/review rule going forward.
- Connection pool sizes (HikariCP, Redis/Lettuce, Kafka client concurrency, gRPC channel limits) become first-class, explicitly documented and load-tested configuration per service rather than an afterthought derived from thread-pool size.
- Observability must add carrier-thread saturation and pinning-event metrics (see validation below) as a standing dashboard, since "thread pool queue depth" — the traditional platform-thread saturation signal — no longer applies the same way.

## When This Decision Would Be Wrong

This decision should be revisited if any of the following becomes true:

- **A service's workload shifts to be predominantly CPU-bound** (e.g. the algorithm engine or a future ML-inference-heavy path grows to dominate a service's request volume) — virtual threads add no throughput benefit there and the added scheduler/carrier-pool complexity is pure overhead; that service should be split out and run on a platform-thread pool sized to cores.
- **A downstream dependency cannot be scaled to match virtual-thread-level concurrency** (e.g. a legacy system integration with a hard connection cap far below what virtual threads let the application generate) — in that case the application-level concurrency must be explicitly throttled (a `Semaphore` or bulkhead), and if that throttle becomes the dominant complexity, a bounded platform-thread pool may be simpler and just as effective.
- **The team cannot keep pinning under control** — if an audit finds pervasive, unfixable native-code pinning (JNI/FFM calls, not `synchronized`, per JEP 491) in a required third-party dependency (rather than our own code), virtual threads for that specific call path provide no real benefit and platform threads (or isolating that dependency behind a dedicated bounded pool) should be used instead.
- **JDK/library ecosystem regression** — if a critical dependency (a JDBC driver, gRPC library) is found to have unresolved virtual-thread compatibility issues (undocumented pinning, thread-identity assumptions) that can't be fixed or worked around, that specific integration point should fall back to platform threads until resolved.

## How We Will Validate It

- **Throughput/latency benchmark, virtual vs. platform threads:** run a fixed-RPS load test (via k6 or Gatling) against a representative I/O-bound endpoint (e.g. task/goal service list endpoint hitting PostgreSQL + Redis) at increasing concurrency (100 → 1,000 → 10,000 concurrent virtual users) on both a platform-thread-pool build and a virtual-thread build. Target: virtual threads sustain p99 latency within 10% of platform threads at low concurrency (200 VUs) and show <20% p99 latency degradation at 5,000 concurrent VUs, where the platform-thread build is expected to degrade by >5x or reject connections outright once pool size is exhausted.
- **AI orchestrator fan-out benchmark:** measure end-to-end latency of a recommendation request that fans out to 4 downstream services, under structured concurrency + virtual threads vs. a `CompletableFuture`-chain baseline on platform threads, at 500 concurrent requests. Target: no more than 5% latency overhead from the virtual-thread/structured-concurrency model versus the raw `CompletableFuture` baseline, in exchange for materially simpler, linear code.
- **Pinning detection in CI/staging:** the `-Djdk.tracePinnedThreads` system property was removed in JDK 24; on Java 25 the standard mechanism is Java Flight Recorder's `jdk.VirtualThreadPinned` event (enabled by default, 20ms threshold, and — as of JDK 24+ — includes a `pinnedReason` field distinguishing native-method/FFM/class-initialization causes). Run load tests with JFR recording enabled and fail the pipeline if any `jdk.VirtualThreadPinned` event is captured on a request-handling path; track a `carrier_thread_pinned_events_total` counter (derived from the JFR stream) exported via Micrometer/OpenTelemetry with an alert threshold of >0 sustained events per minute in staging.
- **Connection pool saturation dashboard:** add Grafana panels for HikariCP `pool.PendingConnections` and `pool.ConnectionCreationTime` (and Kafka/Redis client equivalents) per service; target zero sustained connection-wait queueing under the benchmark load above, using it to right-size pools rather than relying on thread-count as an implicit throttle.
- **Carrier thread pool utilization:** export JVM virtual-thread scheduler metrics (carrier thread count, queue depth) and validate that carrier pool CPU utilization stays correlated with actual CPU-bound work, not blocked I/O — confirming virtual threads are unmounting correctly rather than degrading to pinned/platform-thread behavior under load.
