# Why Virtual Threads?

Both services in LifeOS today — identity-service and task-goal-service — run with `spring.threads.virtual.enabled=true`. That's the whole implementation footprint right now: one config line per service. I want to be upfront that neither service does heavy concurrent I/O fan-out yet, so this isn't a decision I've stress-tested with real traffic. But it's a decision I made deliberately and early, because it shapes how I write code from day one, and retrofitting it later across a fleet of microservices would be much more painful than adopting it before there's much code to migrate.

The reasoning starts from the target shape of the system, not the two services that exist today. LifeOS is meant to grow into roughly a dozen Spring Boot services that are almost entirely I/O-bound — Postgres queries, Redis lookups, downstream service calls, LLM calls, blockchain proof submission. That's the textbook case virtual threads solve: a thread blocked on I/O releases its carrier thread instead of parking an OS thread. The alternative I seriously considered was Spring WebFlux/Project Reactor, which I rejected because it means rewriting the entire call chain — controller, service, repository, every client library — in a non-blocking style, with Mono/Flux everywhere and stack traces that are much harder to read. For a project where I also want to show I can write clear, maintainable code, that cost wasn't worth it when virtual threads give me most of the scalability benefit while keeping the plain synchronous, thread-per-request programming model I already know from Spring MVC.

If someone pushes on "but you haven't proven this scales" — that's fair, and I'd say so directly. What I have today is two CRUD-shaped services with no concurrent fan-out, so virtual threads currently buy me correctness-neutral headroom, not a measured win. Where this actually gets tested is the first time a service needs to fan out — the obvious next case is a dashboard aggregation endpoint that calls several services concurrently, which is exactly the workload virtual threads and structured concurrency (a separate, related decision) are meant for. I also know the sharp edges going in: `synchronized` blocks around blocking I/O pin the carrier thread and quietly degrade back to platform-thread behavior, and `ThreadLocal`-heavy patterns get expensive at virtual-thread scale — which is why request context is planned around `ScopedValue` instead, once there's request-scoped context worth propagating.
