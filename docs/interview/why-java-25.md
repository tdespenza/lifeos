# Why Java 25?

If you ask me why Java 25 instead of Kotlin, Go, or Node.js, the honest answer is that this decision serves two goals at once: build a real, concurrent, I/O-heavy distributed system, and build something that reads well in a senior engineering interview. Java 25 is the first LTS where virtual threads, structured concurrency, and scoped values are all finalized — not preview APIs — at the same time. That matters because the whole point of the future AI orchestrator and algorithm engine is fan-out: calling multiple AI providers concurrently, parallelizing algorithm work. Structured concurrency and scoped values are exactly the primitive I want for that, without reaching for a reactive programming model. Building it on Java 21, where those APIs were still shifting shape release to release, would mean coding against a moving target.

I want to be upfront that I'm not exercising that fan-out concurrency in real code yet. Right now there are only two services — identity-service and task-goal-service — and neither has a concurrent fan-out code path. Virtual threads are turned on (`spring.threads.virtual.enabled=true`) in both, but structured concurrency and scoped values are an intentional next step once a service actually needs to fan out, not something I can point to in production code today. I'd rather say that plainly than imply I've already proven it out.

On the alternatives: Kotlin is a fine language, but running it as the primary language would dilute the "deep Java/JVM" signal I'm optimizing for, and it doesn't buy me anything Java 25 doesn't already have — its coroutines solve roughly the same problem structured concurrency solves. Go's concurrency model is great, but its type system is a weaker fit for the algorithm-engine work that's central to the portfolio goal — the goal dependency-order endpoint, for instance, is a real Kahn's-algorithm topological sort with cycle detection, and Java's sealed interfaces and pattern matching let me encode invariants there in a way Go's type system doesn't support as cleanly. Node.js was the easiest cut: single-threaded event-loop concurrency doesn't demonstrate the JVM-level concurrency depth I'm trying to show, and its type system is weaker for the same invariant-encoding reasons.

The honest tradeoff is that Java 25 is brand new — library and tooling compatibility (Web3j/Besu, GraalVM Native Image, APM/OTel agents) is less proven than on 17/21, so I'm validating each dependency explicitly rather than assuming compatibility, and pinning versions where I have to.
